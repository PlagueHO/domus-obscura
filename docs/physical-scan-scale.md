# Physical scan and process-memory evidence

## Evidence boundary

The generated-record task and the physical task answer different questions.
`scale` checks million-record indexed pagination. It is not a filesystem or
process-memory benchmark.

The physical runner uses fresh generated files and SQLite state. Its small
profile permits at most 4,096 generated files and 1 GiB of total run storage.
Build output and restored dependencies are outside that run-storage allowance.
Do not run a full-size physical fixture on the workstation.

The full profile uses twice the regular-file count in a frozen aggregate library
inventory. It is Azure-only and needs a separate admission record. This document,
an issue plan, or an earlier lab approval does not approve Azure resources.
Do not copy real music into the generated fixture.

Private test processes can exercise the real API and worker without weakening
production network guards. Optimized test-build evidence is not an unmodified
package, installed-service, live-provider or production claim. Keep the separate
browser test harness unchanged.

## Read-only library inventory

Run the inventory from the repository root with an absolute source root. Keep the
output outside Git. Python is required. The operation reads directory metadata,
not media contents. It does not write owner markers or change source permissions.

```powershell
python scripts\physical-scale.py inventory --root '<absolute-library-root>' --output '<new-private-output-file>'
```

```sh
python3 scripts/physical-scale.py inventory --root '<absolute-library-root>' --output '<new-private-output-file>'
```

The output contains aggregate file/byte/format counts and folder distributions.
It does not contain source names or the source root. Windows directory metadata
comes from no-follow handles with retained, non-delete-shared ancestor handles.
Linux enumeration uses directory descriptors and no-follow relative child opens.
Links and reparse points are excluded. Enumeration errors make the count
incomplete and prevent full-profile admission. There is no short-file-ID fallback.

The inventory is not a filesystem snapshot. Keep source changes out of the
counting window where possible. Retain the completed output bytes unchanged;
their SHA-256 binds the full profile. An incomplete count must not silently become
a smaller accepted target.

Generated files reproduce file-count and metadata work, not the library's total
audio bytes or its network storage performance. Record the generated byte count
and filesystem separately from the source aggregate.

## Local checks

```powershell
python scripts\physical-scale-tests.py
.\dev.ps1 scale-physical
```

```sh
python3 scripts/physical-scale-tests.py
cargo task scale-physical
```

The task builds an optimized private test host. It must not enable private
transports in ordinary binaries. Keep fixture generation, protocol peers, the
controller and compilation outside the measured API and worker.

Use `DOMUS_SCALE_OUTPUT` to select a new evidence directory. Keep evidence in a
private session folder or under ignored build output. A failed run must retain a
failure report, not a success-shaped empty result. Never reuse an earlier run's
state or silently overwrite its evidence.

The small dataset has 4,000 initial media files in 64-file folders. It includes
tagged MP3 and FLAC, JPEG, malformed metadata and unsupported audio. A separate
link points to a generated outside sentinel. The share catalog exposes every
eligible initial file and one separate upload file. Acquisition writes to a
different generated root. It does not change the scanned input files.

The worker uses one scan lane, one acquisition lane and a queue capacity of 64.
The fixture runs three downloads, one upload and one complete share listing
through one account login. Local transfer files contain 128 generated MP3 audio
frames. Full-profile transfer files contain 1,024 frames. This is not a network
bandwidth test.

Uploads overlap downloads. The complete listing runs after publication, before
the repeat scan. A listing holds the shared visibility lock and can prevent
publication from taking its exclusive lock. This schedule does not prove that
publication succeeds during a large listing.

Sharing uses its default limits: two upload slots, 128 queued files, 16 queued
files per peer, 64 KiB buffers, 16 peer connections, four pending handshakes and
two concurrent browses. Catalog and expanded-response limits are each 256 MiB.
Compressed responses are limited to 64 MiB. The spool budget is 256 MiB.
The report records the full limit set and actual listing and transfer counts.

The fixture uses the legacy SQLite provider cache, not the optional file cache.
The catalog body budget is 16 MiB and 64 entries. Inspection records occupied
catalog body bytes and entries. It does not measure each SQLite connection's
page-cache occupancy. Total generated storage includes the database, WAL,
spools, output files, logs and evidence. Spool high-water occupancy is not
reported separately. Live storage samples allow expected entry deletions and
renames; other access errors fail the measurement. Windows storage handles allow
delete sharing, and the final total is checked after child processes stop. Live
samples are traversals, not atomic filesystem snapshots.

## Memory interpretation

The threshold is **536,870,912 bytes**, or 512 MiB, for API plus worker resident
memory. It is not a per-process allowance.

Windows uses current and peak working-set counters. Linux uses resident pages
from `smaps_rollup` and collects each owned child's final peak RSS through
`wait4`. Its running `VmHWM` values remain subject to the kernel's accuracy limits.
Virtual memory, browser memory and allocator counters are not substitutes.
Bind each measured PID to its start identity.

Pair current API/worker readings and keep raw timestamps. Paired reads are
sequential, not an atomic snapshot. Shared resident pages count in both processes.
Report a sampled combined maximum separately from the sum of per-process peaks.
Those peaks can occur at different times. Their sum is a conservative bound,
not an observed simultaneous peak. A single process peak above the limit proves
failure; a larger sum of noncoincident peaks alone remains inconclusive.

Sequential worker restarts do not overlap. The conservative bound uses the
largest worker-segment peak plus the API lifetime peak, not the sum of all
worker-segment peaks. Each segment retains its own process start identity.
The steady workload window starts one second after the first observed download
start and ends at the last observed download completion. It must last at least
two seconds. The report retains the exact window beside the raw sample times.

A combined sample above the threshold fails. A sample below the threshold does
not prove that unsampled peaks passed. Missing phases, process identity changes,
measurement gaps or incomplete peak evidence must produce an incomplete or
inconclusive result. A profile-specific result must not close broader acceptance.

Record workload settings and actual overlap. This includes scan progress,
transferred bytes, upload slots, listings, queue capacity, lane concurrency,
connections, cache budgets, cache occupancy, spool use and image sizes.
Idle processes alone cannot prove the active-workload target.

## Full Azure admission

Do not provision as part of a scale command. Before any provisioning, obtain
separate approval for the exact subscription, region, native Windows and Ubuntu
24.04 x86_64 images, VM count/SKUs, disk sizes, total cost ceiling, runtime limits,
guest tools and identities, private evidence transfer and cleanup targets.
Inspect current prices and image availability at execution. Do not copy private
Azure identifiers into public issue evidence.

Use one VM at a time, no public inbound ports and an independently verified
cleanup control outside the workload. No failed setup approves a replacement VM,
extra disk, extended deadline or additional cost. Do not provision if the full
generated dataset and its database/cache/output reserve cannot fit the approved
limits. Do not lower the target silently.

The private admission JSON must contain:

| Field                        | Required value                                         |
| ---------------------------- | ------------------------------------------------------ |
| `schema`                     | `1`                                                    |
| `baseline_sha256`            | SHA-256 of the exact complete inventory file           |
| `platform`                   | `Windows` or `Linux`, matching the guest               |
| `azure_only`                 | `true`                                                 |
| `separate_resource_approval` | `true`                                                 |
| `cleanup_verified`           | `true`, after independent cleanup verification         |
| `approval_reference`         | Reference to the actual separate approval              |
| `vm_id`                      | Exact approved VM identity, checked through Azure IMDS |
| `max_run_bytes`              | Positive approved total run-storage bound              |
| `deadline_unix`              | Future absolute deadline in Unix seconds               |
| `max_runtime_seconds`        | Positive approved finite runtime bound                 |

Full Linux admission also requires `linux_permission_fixture_approved: true`.
Obtain separate approval for that generated-file permission change first.
The controller opens each component without following links, changes the exact
file through its retained descriptor, verifies an actual denied open, and restores
the original mode. Root or other access that bypasses the denial fails the check.
Small Linux CI profiles do not change permissions and leave that evidence open.

These fields record approval. Setting them is not itself permission to create
resources. The VM identity check uses the fixed Azure metadata endpoint without a
proxy, redirect or retry.

Set `DOMUS_SCALE_MANIFEST`, `DOMUS_SCALE_ADMISSION` and `DOMUS_SCALE_OUTPUT` to
private absolute paths. Then use `.\dev.ps1 scale-physical-full` on Windows or
`cargo task scale-physical-full` on Linux. Keep both systems on the same source
revision and frozen baseline. Export evidence before deleting the exact
task-owned resources. Verify deletion explicitly.

## Acceptance status

The read-only baseline completed without enumeration errors. It observed
**34,872 regular files** in **3,139 directories**. The resulting full generated
target is **69,744 files per system**. The source logical-byte count was
198,752,789,549 bytes. That byte count is not a request to copy or reproduce the
music contents.

This user-selected target is below the more-than-500,000-file operating context
in `PRODUCT.md`. It cannot prove physical traversal at that larger size. The
separate million-record database checks must not be used to fill that evidence gap.

The frozen aggregate manifest has SHA-256
`028b8541103de8b2cf1ab5ee3456e2d8b99b017d1b9ea60c60273f4eb14f1c27`.
The manifest is private session evidence. It is not a filesystem snapshot.

Full-size Windows/Linux physical traversal and combined active-workload memory
acceptance remain open until both native result sets exist. Keep local, CI and
Azure results separate. A fixture, a test command or a small-profile pass is not
full-size evidence.

If a threshold fails, retain the failed value and workload. Identify required
changes. Run changes as a new profile result instead of rewriting the original.
